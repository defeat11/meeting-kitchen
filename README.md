# meeting-kitchen

[English](README.en.md)

**ضغطة زر على تابلت في غرفة الاجتماعات ← طلب على شاشة المطبخ ورسالة في Power Automate.**

> **هذا النظام يعمل في بيئة إنتاج لدى جهة عملي، والكود ملكها. هذا المستودع يوثّق المعمارية والقرارات الهندسية وطريقة البناء.**

نظام ضيافة كامل في 5,851 سطراً: تطبيق PWA على تابلت الغرفة، و PHP API فيه 15 endpoint،
وشاشة مطبخ تتحدّث لحظياً، وتطبيق Android فيه foreground service ينبّه، و Webhook يروح لـ Power Automate.

الاستضافة shared hosting: ما فيه غير PHP و SQLite. لا Node، ولا WebSocket، ولا push notifications.
كل قرار في النظام تشكّل عشان هذا القيد.

---

## المشكلة

طلب الضيافة في الاجتماع لازم يمر على شخص. يعني الموظف يطلع من الغرفة، أو يتصل، أو يقعد ينتظر.

واستدعاء الدعم الفني أسوأ: ما فيه سجل لا لوقت الطلب ولا لمين استلمه.

المطلوب: زر واحد جوّا الغرفة. والطلب يوصل المطبخ أكيد، حتى لو الشاشة مطفية أو الشبكة راحت.

---

## كيف يشتغل

| المكوّن | الوظيفة |
|---|---|
| تابلت الغرفة (PWA) | شاشة طلب بدون login. رقم الغرفة محفوظ في التابلت نفسه، فكل طلب يجي ومعه اسم غرفته |
| العمل بلا إنترنت | Service Worker يحفظ الواجهة. لو انقطع النت، الطلب يقعد في queue محلي ويطلع أول ما يرجع |
| واجهة PHP | ملف واحد على نمط `?action=`، فيه 15 action و 6 جداول SQLite. أي query فيه مدخل من المستخدم يمر على prepared statement (22 عبارة)، والباقي SQL ثابت ما يتركّب من نصوص |
| شاشة المطبخ | تسحب `feed` كل 5 ثوانٍ ومعها مؤشر `after`، فما ينزل إلا الجديد والشغّال. صوت واهتزاز أول ما يجي الطلب |
| تطبيق أندرويد | WebView مع foreground service يسحب كل 8 ثوانٍ، ويطلّع notification من النظام والشاشة مطفية |
| **Power Automate** | كل استدعاء يطلق Webhook من الخادم، والـ payload هو `{type, label, room, note, time}` |
| الواجهة | عربي أولاً (RTL) وإنجليزي كامل: 182 مفتاح ترجمة، كلها في ملف واحد |

**مسار الاستدعاء إلى Power Automate:**

```
تابلت الغرفة ──POST action=call──> PHP API ──INSERT──> SQLite
                                      │
                                      ├──> شاشة المطبخ + تطبيق أندرويد (سحب feed)
                                      └──> POST JSON ──> Power Automate (HTTP trigger)
                                                              └──> Teams / بريد / مهمة
```

عنوان الـ Flow محفوظ في جدول `settings`، وتغيّره من شاشة إعدادات المطبخ.
ما هو مكتوب في أي ملف كود، ولا موجود على أي تابلت.

## أهم قرار في التصميم

**المشكلة:** الاستدعاء لازم يوصل Power Automate. بس أي HTTP call لسحابة برّا ممكن يتأخر
أو يفشل. لو قعد الخادم ينتظره، يظل الموظف واقف قدام زر معلّق.

**القرار:** الخادم يحفظ الاستدعاء في SQLite أول شي، بعدها يطلق الـ Webhook داخل `try/catch`
بمهلة اتصال ثانيتين ومهلة كلية 3 ثوانٍ. لو فشل الـ Flow، رد الـ API ما يتغير أبداً.

**التكلفة والعائد:** أسوأ حالة 3 ثوانٍ زيادة على طلب واحد. مقابلها إن الاستدعاء محفوظ
وطالع على شاشة المطبخ، حتى لو Power Automate واقف تماماً.

قاعدة البيانات هي المرجع. الـ Flow قناة تنبيه زيادة، مو شرط عشان الطلب ينجح.

نفس السبب خلّى الإطلاق يصير من الخادم مو من المتصفح: عنوان الـ Flow ما ينزل على تابلت في غرفة مفتوحة.

## ماذا في هذا المستودع

الكود ملك جهة العمل، فما هو هنا. المستودع يوثّق المعمارية وطريقة البناء والنشر.

بنية النظام في الإنتاج:

```
htdocs/
  index.html app.js kitchen.html kitchen.js settings.html settings.js
  config.js styles.css manifest.json sw.js icons/
  api/  index.php  db.php  data/   ← يُنشأ عند أول طلب، محميّ بـ .htaccess
```

طريقة النشر، مثل ما تصير فعلاً:

1. ترفع الملفات في جذر الاستضافة المشتركة. قاعدة البيانات تنبني وتتعبّى بالبيانات الأولية لحالها عند أول زيارة.
2. تفتح `settings.html` على التابلت، تختار اسم الغرفة، وتثبّت الصفحة على الشاشة الرئيسية.
3. ما فيه كلمة مرور مكتوبة في الكود: تضبط `KITCHEN_USER` و `KITCHEN_PASSWORD` في environment،
   أو النظام يولّد كلمة عشوائية يكتبها مرة وحدة في ملف ينحذف بعد أول دخول.
4. تلصق عنوان الـ Flow في تبويب الإعدادات — ومن هاللحظة كل استدعاء يوصل Power Automate.

قبل أي رفع، الملفات تمر على فحص آلي: PHP lint لكل ملف خادم + تأكد إن كل JSON سليم. ما يطلع شي إلا بعد `VERIFY: PASSED`.

## لماذا بنيته

أنا مشرف تقنية معلومات، وطلبات غرف الاجتماعات كانت تجيني بالكلام أو متأخرة.

الحين الاستدعاء الواحد يوصل 3 جهات: شاشة المطبخ، وإشعار الجوال، و Power Automate.
